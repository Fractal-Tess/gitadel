Core feature investigation · v0.1 working tree

Build deeper,
not broader.

Gitadel already has enough forge surface. Its next features should make repositories easier to control, replicate, verify, and recover—not make people collaborate inside it.

Codebase + git history 7 comparable products 28 primary-source URLs checked

TL;DR

The right category is not “small GitHub.” It is a self-hosted repository appliance: Git transport, durable identity and access, high-quality read-only browsing, replication, and provable recovery.

Recommendation

Complete repository lifecycle first; add preservation and machine-access primitives second; harden the in-progress webhook work on top of a durable jobs/outbox layer.

Control

Default branch, archive, rename, transfer, delayed delete, and explicit permissions.

The product lane

Gitadel sits cleanly between cgit/Gitolite and Forgejo/Gitea: more integrated than a browser plus ACL layer, dramatically narrower than a collaboration suite. Soft Serve is the closest scope comparator; Gitadel's stronger differentiator is its portable instance and integrity-checked backup model.

Category What it optimizes for Gitadel's stance
cgit / gitweb Fast read-only browsing and source distribution Keep their restraint; add integrated identity and lifecycle.
Gitolite SSH authorization and ref-level policy Borrow protected-ref semantics, not its configuration model.
Soft Serve Small, self-hosted Git service with import/mirrors/webhooks Closest feature boundary; compete on preservation and web browse quality.
Forgejo / Gitea / GitLab Full software-development platform Borrow operational patterns only; reject collaboration subsystems.
Radicle Location-independent, verifiable replication Borrow stable identity and independently verifiable copies, not P2P.

Current baseline

The data plane is already credible. The control plane and operator plane are where the product still feels like v0.1.

Area Status Finding
Git + LFS transport Strong SSH push/clone, Smart HTTP fetch, private token-authenticated HTTP fetch, LFS and locks. Smart HTTP push is missing.
Source browsing Strong Tree, blob, raw, branches, tags, commits, diffs, Markdown, highlighting, activity, and language stats.
Identity and human access Strong Passwords, passkeys, sessions, API tokens, SSH keys, OAuth, invitations, organizations, collaborators, and audit records.
Repository lifecycle Thin The schema models default branch and archive state, but there are no shipped controls for default-branch repair, archive/unarchive, rename, transfer, or delete/restore.
Preservation Partial Instance backups are checksum-manifested and restore into empty storage. There is no portable per-repository export/import, fsck workflow, or automated restore proof.
Automation In progress OAuth and narrow Gitea discovery support Dokploy. Uncommitted webhook code exists, but is not ready to ship safely.
Operations and scale Thin Database health only, no rate/concurrency/storage limits, no metrics, no CI workflow, and expensive all-repository overview work.
Important asymmetry: the README says HTTP fetch is public-only, but the current Git HTTP code accepts scoped tokens for private repositories. Document and test that behavior; do not rebuild it.

What to add

These are ordered by product fit and risk reduction, not by novelty. The first three are the heart of the product.

01P0 · NOW

Repository lifecycle and correct HEAD

Add owner-managed description, visibility, default branch, archive/unarchive, atomic rename/transfer, and delayed delete/restore/purge. The immediate bug to eliminate is hard-wiring every new repository to main, which makes a first push to master browse incorrectly.

  • Changing the default branch updates symbolic HEAD.
  • Archive remains browsable/cloneable and rejects all writes.
  • Rename/transfer preserve immutable repository ID and storage key.
  • Delete is reversible before an audited purge deadline.
Medium–LargeHighest product value
02P0 · NOW

Preservation: import, export, verify, restore

Add a one-shot remote import and a Gitadel-independent per-repository export: full Git bundle, HEAD, versioned metadata, and referenced LFS objects. Add git fsck --strict, LFS digest verification, backup verify-only, and a clean-host restore test.

  • Import preserves every branch, tag, note, default branch, and LFS object.
  • Export can be cloned or restored without a Gitadel server.
  • A restore drill compares every advertised ref/OID and exercises SSH + HTTP clone.
  • Interrupted restore has rollback or a documented resumable recovery path.
LargeCore differentiator
03P0 · FOUNDATION

Durable jobs/outbox layer

Build one bounded, persistent mechanism for post-push work. Use it for webhook delivery, mirror synchronization, integrity checks, Git maintenance, and expensive stats refresh. This prevents each feature from inventing its own detached task and retry behavior.

  • Persisted job state, attempts, next-run time, last error, and idempotency key.
  • Per-repository serialization where mutation is involved.
  • Global concurrency, timeout, backoff, and retention controls.
  • Queue depth and failure metrics.
MediumUnblocks 4 epics
04P0 · BEFORE 1.0

Machine access and write safety

Add scoped-token Smart HTTP push, repository deploy keys (read-only by default), and minimal protected refs. This gives CI/deploy systems a least-privilege path without introducing reviews or branch workflows.

  • receive-pack requires write scope and repository authorization.
  • Deploy keys are repository-scoped, expiring/revocable, audited, and show last use.
  • Default branch and selected patterns can reject force-push and deletion.
  • Protocol v2, shallow clone, fetch, and push have transport integration tests.
LargeTransport parity
05P0 · BEFORE MERGE

Finish webhooks as an external automation boundary

The live uncommitted webhook implementation is directionally right—push-only JSON, optional HMAC, no arbitrary server hooks—but it must move onto the outbox and adopt strict destination policy before shipping.

  • Block loopback, link-local, metadata, and private-network destinations by default; revalidate DNS and redirects.
  • Persist delivery history; retry with backoff; support bounded replay.
  • Stream/cap response bytes and delivery concurrency.
  • Emit the exact Gitea/GitHub fields and headers required by the named Dokploy contract.
MediumCode already WIP
06P0 · BEFORE 1.0

Operational guardrails

Bound the work that public browse, Git subprocesses, LFS, imports, and downloads can consume. Split liveness from readiness and expose a small protected metrics surface.

  • Rate, body, process-concurrency, LFS object/batch, repository, and disk-watermark limits.
  • Paginated repository lists and cached/precomputed overview statistics.
  • Streaming raw/diff/archive responses with time and size limits.
  • Readiness covers database, repository/LFS storage, key material, and disk space.
Medium–LargeInternet safety
07P1 · NEXT

Admin recovery and permission repair

Add user list/disable/enable, session revocation, invitation revocation, admin promotion, and a locked-out-admin recovery command. Clarify or fix organization semantics: today every organization member can write every organization repository, while repository collaborators work only for personal repositories.

MediumOperator confidence
08P1 · NEXT

Read-only distribution and discovery

Add immutable-revision source archives (tar.gz/zip), blame, repository/branch/tag pagination, repository size/LFS inventory, and bounded path or commit-message search. Add full code search only after measured demand.

Suggested build sequence

Avoid parallel feature islands. Establish lifecycle invariants and one background-work primitive first.

Phase 1 · Control

Make repository state real

  • Default branch + HEAD
  • Archive/unarchive
  • Rename/transfer
  • Delayed delete/restore
  • Jobs/outbox schema
Phase 2 · Preserve

Prove the archive promise

  • Full-ref import
  • Bundle + LFS export
  • fsck + LFS verification
  • Atomic/resumable restore
  • Restore drill in CI
Phase 3 · Integrate

Serve machines safely

  • Smart HTTP push
  • Deploy keys
  • Protected refs
  • Durable signed webhooks
  • Pull mirror, then push mirror

Release gate for every phase: backend tests, Svelte check/build, formatter + Clippy, Docker smoke, NixOS smoke against the real /healthz route, and transport/backup end-to-end tests in committed CI.

Risks found during the audit

These are not reasons to widen scope; they are reasons to make the existing scope dependable.

Webhook SSRF

The uncommitted URL validator accepts any HTTP(S) host, including loopback/private/metadata targets. Detached deliveries are unbounded and not durable. Do not merge as-is.

Unbounded browse

The overview traverses every accessible repository and reachable history; raw blobs and diff subprocess output are buffered; caches and Git process counts are unbounded.

Restore split-brain

Restore verifies archive checksums but installs repositories, LFS, database, and host key through separate renames. A mid-install failure can leave a partial target that blocks a clean retry.

Permission surprise

Every organization member currently receives write access to every organization repository. Per-repository collaborators are restricted to personal repositories.

Address mismatch

Clone URLs use the internal SSH bind port. A custom externally published Docker Compose SSH port can produce the wrong URL.

Quality gate

No committed CI workflow exists. The audited tree passed 12 Rust tests and Svelte diagnostics/build, but Rust emitted dead-code warnings and the frontend bundle reported oversized chunks.

Keep these out

A useful rule: if a feature needs conversations, assignments, approvals, notifications between people, or repository-owned code execution, it does not belong in Gitadel.

Pull requestsIssuesReviewsCommentsSocial graphsFork networksWikisBrowser editingCI runnersPackage registriesUser shell hooksFull Gitea parityRelease objects—for now

Use tags, immutable source archives, raw files, Git LFS, and signed webhooks instead. Those cover source distribution and automation without creating a second collaboration platform.
